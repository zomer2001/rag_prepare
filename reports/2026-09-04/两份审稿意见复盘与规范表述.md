# 两份审稿意见复盘与规范表述

> 日期：2026-09-04  
> 目的：区分真正击中方法的问题、因原报告表述夸大造成的攻击面，以及审稿意见自身的过度推论。

## 1. 总结判断

两份意见的共同核心是对的：原报告把“表示结构”“检索方法”和“Planner”并列成三项创新，造成了方法驱动而不是问题驱动的叙述。更严重的是，当前 EventEffect 六分类确实混合了不同语义层次。这不是审稿人误读，而是代码和本体目前都存在的问题。

但第一份意见把“表示原语已有”进一步推成“整个任务和方法几乎已有”，这个结论过头。Graphiti、PROV-O、CIDOC-CRM、ProPara/OpenPI 分别证明双时态记忆、溯源、事件中心建模和状态变化表示早有研究；它们足以否定“我们发明了事件—事实—来源表示”的宽泛 novelty，却不等价于“按问题要求检索一组角色完整、相互连接、带来源的演化证据”。后者仍可能成为研究问题，但目前尚未被严格定义和验证。

因此应同时完成两件事：

1. 撤回 Event-Effect Ontology 本身的新颖性主张，并修正其语义模型；
2. 把论文主轴改为可测量的 query-conditioned lifecycle evidence retrieval，而不是换一个更响亮的新名词后继续做普通扩图。

## 2. 哪些意见真正有建设性

| 意见 | 判断 | 为什么 | 必须采取的行动 |
|---|---|---|---|
| EventEffect 六分类混合世界状态变化、来源立场和断言版本关系 | **完全成立，且是最高优先级问题** | 当前代码把 creates/updates/terminates/supersedes/denies/confirms 放在同一枚举中；denies/confirms 还会直接改变 Assertion 状态 | 拆成 TransitionEffect、MentionStance、AssertionSuccession 三层 |
| valid time 与 observation/publication/recorded time 需要区分 | **成立** | 当前模型已有 `valid_from/to`、Mention `published_at` 和 `recorded_at`，但论文未定义三者语义，查询也未充分利用 | 明确定义事实有效时间、来源发布时间、系统记录时间；不再笼统写“时间” |
| “完整证据”没有形式化定义 | **完全成立** | old-event-new 不是所有问题都需要；固定六槽会形成自定义目标与自定义指标的循环论证 | 由问题类型确定 required role set；完整只能相对于标注角色集合定义 |
| EvoNeed 目前不是检索前规划 | **完全成立** | 当前第一轮仍执行完整 EvoLink，Recall 不变且延迟大幅增加 | 不再列为独立贡献；若保留，改成首轮 role→route/query/budget 控制器 |
| MultiHop-RAG、ChronoQA、HoH 均不能单独验证核心主张 | **成立** | 它们分别验证一般多跳、叙事时间因果、过时信息干扰，缺少“事件改变哪条事实”的完整标注 | 基于真实来源增加生命周期角色标注集；三个现有数据集只承担子问题验证 |
| Temporal-only 是 killer baseline | **非常有建设性** | 若只靠共享 subject/predicate 和有效期前后继就能达到同样效果，Event transition 没有必要 | 主消融增加 temporal adjacency / bitemporal-only |
| Graphiti-style bitemporal invalidation baseline | **成立** | Graphiti 是当前表示和增量记忆最接近的工程先例 | 加入相关工作；实现受控的双时态边基线，不必宣称完整复现生产系统 |
| Gold EventEffect vs predicted EventEffect | **完全成立** | 能直接区分检索算法上限和抽取瓶颈 | 提升为主实验，而不是附录 Oracle |
| 测试 stance 被生成模型误当成真相 | **成立** | `denies` 是来源立场，不代表事实被证伪；当前状态渲染可能误导模型 | 新增 stance-truth confusion / unsupported resolution 指标和反事实测试 |
| updates 与 supersedes 边界含糊 | **成立** | 真实文本中修改事实、产生新版本、替换对象的界限需要操作性定义 | 先降为 creates/modifies/terminates；succession 单独建边，细分类仅在一致性足够时保留 |
| 先做能证伪自己的实验 | **完全成立** | 当前最需要判断 EventEffect 是否必要，而不是继续堆模块 | 优先 temporal-only、untyped、typed、randomized、oracle 五级对照 |
| FRESCO、When Facts Change、ATOM、SR-RAG 应补入综述 | **成立** | 它们分别覆盖演化冲突重排、时间知识冲突、双时态 TKG 构建和动态子问题/符号验证 | 加入相邻工作，明确任务差异，不再只检索“RAG 图方法” |

## 3. 哪些批评是原报告自己制造的

### 3.1 把 Event-Effect Ontology 写成创新

原报告受“本体能否让故事更强”的讨论影响，把仓库中已有 OWL/SHACL 文件从“结构契约”抬升成了论文贡献。这是错误的叙事升级。

存在 OWL 类、SHACL 约束和 PROV-O 对齐，只能说明实现使用了本体化 schema，不能说明本体概念新颖，更不能自动说明存在推理贡献。PROV-O 本来就定义实体由 Activity 生成或使其失效，Nanopublication 也长期区分 Assertion、Provenance 和 Publication Info。

**规范说法：**

> 我们使用来源感知、带时间的证据图作为检索表示，并复用既有溯源与时间建模思想。表示本身不是本文主要新颖性；它服务于按问题约束进行证据集合检索。

不要再写：

> 我们提出一种新的事件作用本体，实现全周期推理。

### 3.2 把一种常见模式写成普遍的“完整证据”

旧状态—变化事件—新状态是很好的例子，但不是所有问题的固定答案结构。原报告把例子写成了任务定义，导致审稿人可以用“CEO 离职但继任者未知”等反例推翻它。

**规范说法：**

> 每个问题对应一个由标注或预测得到的证据角色集合。某次检索的角色覆盖是否完整，仅相对于该问题所需角色判断；并非每个问题都必须包含前态、事件和后态。

### 3.3 把 Planner 的计划能力写在实现前面

当前 EvoNeed 只能在完整检索后评估和排序证据。旧报告虽然承认这一点，却仍把未来设计列作“创新 3”，给审稿人留下未实现贡献的攻击面。

**规范说法：**

> 当前 EvoNeed 是一个昂贵的证据评估/重排原型。只有在它能够于检索前预测角色并改变路线或预算，且改善质量—成本 Pareto 后，才保留为方法组件。

### 3.4 把小幅 q100 结果解释得过多

MultiHop-RAG q100 能说明系统可运行，以及跨视图链接在普通多文档检索中出现小幅正向信号；它不能说明生命周期语义有效。

**规范说法：**

> q100 结果是实现检查和一般检索的开发集信号，不是 lifecycle claim 的证据。

## 4. 哪些审稿意见本身推得过头

| 审稿说法 | 偏差在哪里 | 应如何吸收 |
|---|---|---|
| Graphiti 与 ELC-RAG “功能层面几乎是一回事” | Graphiti 的任务是动态 agent memory；它证明双时态事实、历史保留和 provenance 不是新概念，但没有以 query-specific lifecycle role coverage 为评测目标，也没有显式事件证据集合任务 | 作为最接近的工程/记忆系统先例和双时态基线，不把它说成同任务，也不能忽略它 |
| PROV-O/CIDOC-CRM 已经完成 Event 创建/修改/终止可追溯 Assertion | PROV-O 明确支持 Entity 的生成、失效和 provenance；CIDOC-CRM 是事件中心历史描述。本体原语高度相关，但不等于开放域文本抽取或 RAG 证据补全算法 | 撤回表示 novelty；把这些工作作为建模来源，不把它们包装成直接检索竞品 |
| ProPara/OpenPI 与 EvoNeed “几乎同构” | before/after 状态表示确实相似，但它们处理单篇程序性文本中的实体状态跟踪，不处理跨来源开放域检索、来源冲突或证据集合选择 | 必须引用为状态变化表示先例；任务差异要明确 |
| q100 “实际上什么都没有证明” | 说得过头。它证明实现工作且在一般多文档检索上有小幅行为差异，只是不能归因到 lifecycle | 降级为开发结果，不删除它，也不放在核心结论位置 |
| Graphiti “亚 300ms”应直接与 12.3s 比较 | 缺乏同语料、同硬件、同查询、同生成边界和同质量指标；Zep 论文报告相对延迟改进，但不能直接拿一个工程数字做公平排名 | 只做同协议受控比较；外部生产数字作为背景，不进入主表 |
| 三个现有数据集“均不匹配” | 它们不是核心任务的完整评测，但各自能验证子能力：MultiHop 测跨文档，ChronoQA 测时间/事件，HoH 测旧信息干扰 | 按子问题使用，同时承认必须补直接标注集 |
| “首次定义 Lifecycle Evidence Retrieval”一定成立 | 尚未完成系统性检索，evidence completeness、reasoning-chain completeness 和动态检索已有邻近工作 | 不写“首次”；写“我们研究并操作化这一设置”，新颖性由任务定义、数据和对比共同支持 |

## 5. 当前模型应如何改干净

### 5.1 四层语义

```text
World claim:
  Assertion(subject, predicate, object, valid_time)

World transition:
  Event --creates/modifies/terminates--> Assertion

Assertion succession:
  Assertion_new --replaces/supersedes--> Assertion_old

Source stance:
  Mention --supports/contradicts/retracts/uncertain--> Assertion
```

`denies` 和 `confirms` 从 EventEffect 移出；`supersedes` 不再只作为 Event→Assertion 的 effect，而应显式连接新旧 Assertion。第一版可将 effect 降为 `creates/modifies/terminates`，等人工标注一致性足够后再细化。

### 5.2 三类时间

- `valid_time`：报道声称事实在现实世界何时有效；
- `publication/observation_time`：来源何时发布或观察到该说法；
- `recorded/transaction_time`：系统何时接收和保存该记录。

这些都是“来源中抽取或系统记录的时间”，不得无条件写成客观真值。

### 5.3 不再使用含糊的全局状态

`active/inactive/disputed` 容易被理解成系统已经裁决事实。更安全的是：

- 保存每个 Mention 的 stance；
- 保存每条 Assertion 的 claimed valid interval；
- 保存系统推导标签的依据和规则版本；
- 对未裁决冲突使用 unresolved/conflicting-evidence；
- 给生成器明确提示：来源否认不等于事实已被证伪。

## 6. 新的任务与指标表述

给定问题 `q`，定义其所需证据角色集合 `R(q)`。角色由问题类型、人工标注或预测器确定，例如：

- current-state：当前状态、有效时间、来源；
- historical-state：历史状态、有效区间、来源；
- change-cause：变化前状态、变化事件/原因及其来源，后态按问题需要可选；
- trajectory：多个按时间连接的状态与事件；
- conflict-verification：互相支持/反驳的来源、时间及未决冲突。

候选集合 `E` 只有在满足下列条件时才称为 **role-complete**：

1. 覆盖 `R(q)` 中所有必需角色；
2. 每个角色由可定位的来源片段支持；
3. 角色之间存在标注允许的时间、transition、succession 或 stance 连接。

“完整”必须是相对于 `R(q)` 的，不是绝对完整。允许一个问题存在多个可接受的最小证据集合，不能强制唯一 Gold Set。

推荐指标：

- Lifecycle Role Recall@K；
- Role-Complete Retrieval@K（所有必需角色均覆盖）；
- Source Traceability@K；
- Connected Evidence Rate@K；
- Stale-only Retrieval Rate；
- Missing-transition Rate；
- Stance-as-truth Error；
- 标准 Recall/nDCG/MRR 和下游答案/引用指标。

## 7. 规范后的论文主张

### 问题

> 当来源中同时存在同一事实的历史状态、后续状态和相关变化事件时，逐片段相关性检索可能返回若干相关文本，却遗漏回答该问题所必需的某类证据。本文研究如何在固定证据预算下，提高按问题定义的生命周期证据角色覆盖，并保留各角色之间的连接和来源。

### 方法假设

> 若检索器显式预测问题所需的生命周期证据角色，并只沿能够满足缺失角色的时间、transition、succession 和 provenance 路径扩展，那么它应比无约束图扩展或单纯时间排序更容易获得 role-complete evidence set。

### 不再主张

- 不声称发明事件—事实—来源表示；
- 不声称本体文件本身是主要创新；
- 不声称每个问题都需要 old-event-new；
- 不声称系统裁决客观真相；
- 不声称当前 EvoNeed 已完成检索前规划；
- 不用 MultiHop q100 证明生命周期语义有效；
- 不使用“据我们所知首次”，除非完成系统综述并限定范围。

## 8. 修订后的优先实验

1. **模型语义修正前的审计**：统计六类 Effect 分布，人工检查 denies/confirms/supersedes 的错误传播。
2. **Temporal-only vs untyped vs typed vs randomized**：直接判断 Event transition 是否必要。
3. **Gold transition vs predicted transition**：量化抽取误差上限。
4. **Role-complete benchmark**：在真实新闻/公告或真实历史版本上标注 query、required roles、证据片段、连接和多个允许证据集合。
5. **LLM decomposition + ordinary Hybrid/KG expansion**：判断专门角色结构是否优于普通子问题拆分。
6. **Graphiti-style bitemporal baseline**：只用双时态关系和旧边失效，不使用显式事件。
7. **结构呈现安全实验**：相同正文下比较无标签、正确标签、打乱标签，并测 stance 被误用为真相的比例。

只有上述实验显示 role-constrained transition expansion 在相同预算下优于 temporal-only、普通分解和无约束扩图，论文主轴才真正成立。

## 10. 最终复盘

第一份意见最大的价值是补齐了跨社区先例，最大的偏差是把“原语相似”扩大成“任务等价”。第二份意见最有价值的地方是识别了 EventEffect 的语义混层、“完整证据”未定义、算法仍是普通扩图和数据集不匹配；这些必须接受。

原报告的问题不是文笔不够学术，而是概念没有先分干净，却提前使用“本体、生命周期、推理、完整”等强词。以后每个强词都必须绑定一个可观察对象：

- 本体 → 明确公理/约束/推理及其增益；
- 生命周期 → valid/observation/transaction time 与 transition；
- 完整 → query-specific required roles 的覆盖；
- 推理 → 可复现规则或明确的模型操作；
- Planner → 检索前实际改变 route/query/budget；
- 有效 → 相同预算下的指标、显著性和错误分析。

只要遵守这套口径，审稿人就很难再因为我们的夸大表述抓住一个词反复攻击；剩下的问题将回到真正应当通过实验回答的科学假设。
