# EvoLink 现状与本体建模差距报告

> 日期：2026-09-02
> 代码基准：`v2_tkg` 当前工作区
> 结论口径：只写已经实现或已有实验支持的内容，不把规划当成果。

## 1. 先说结论

EvoLink 当前最准确的定位是：**把原文、实体关系和事件演化保留为三种独立知识视图，再用统一实体、事件对事实的生命周期作用和来源证据，把三路在索引期与查询期连接起来。**

它已经是一个可运行的、带静态本体约束的声明级时序知识融合与检索原型，但还不是完整的本体驱动系统，更不是动态本体系统。现有实验说明完整系统在一个小规模多跳检索子集上有更好的证据覆盖；没有充分证明增益单独来自 EvoLink，也没有证明对所有数据集、所有模态或所有外部方法都占优。

## 2. 当前 EvoLink 真正能算的创新点

### 2.1 事件不只是另一路文本，而是关系事实的状态变化原因

系统把稳定事实建成 `Assertion`，把事件建成 `Event`，再用 `EventEffect` 表达事件对事实的 `creates / updates / terminates / supersedes / denies / confirms` 作用。这样可以保留旧事实、当前事实、变化时间和导致变化的来源，而不是把新旧三元组同时当成真。

这是当前最有辨识度的机制：**显式连接“发生了什么”和“哪条关系因此发生了什么变化”。**

### 2.2 三路保持差异，同时能跨路补证

原文 Chunk、语义 Assertion、事件 Event 分别索引和召回。查询时，EvoLink 从问题中的实体、语义图命中的实体以及事件命中的 `event_id` 取种子，在 Neo4j 中扩展 Entity—Assertion—Event—Effect—Mention 邻域，再把补到的关系证据和事件证据送回各自通路。

这不是把三份结果简单拼接：一个实体命中可以补出相关事件，一个事件命中也可以补回受影响的关系事实及其原文来源。

### 2.3 融合后仍保留证据角色和来源

实体、Assertion 和 Event 都通过 Mention 回到 `document_id` 与 `source_segment_id`。最后按父文档做 RRF，EvidenceBundle 仍记录该文档由 vector、graph、event 哪些通路命中，并优先保留每路一条代表性原文。

因此系统交付的不是一个无法解释的统一向量，而是可回到来源的证据组合。

### 2.4 哪些不能单独称为创新

- 三路检索、Embedding、Neo4j、RRF 和 Query Planner 本身都是已有技术或常规工程组合。
- `ours`、事件通路和 EvoLink 同时变化时，整体指标提升不能全部归因于跨图连接。
- 当前固定版 `ours_evolink` 实际上三路全开，比较适合说“协作机制”，不适合说已经学会动态最优路由。
- 现有 n30 只验证文本化语料，不能据此声称已经完成图片、表格、音频、视频的端到端多模态验证。

## 3. 实现方法

### 3.1 索引阶段

1. 文档被切成带稳定 `document_id/source_segment_id` 的 Chunk，进入原文向量通路。
2. 受控语义抽取每个片段最多保留 4 个关键实体和 4 条关键关系，进入 Entity—Assertion—Mention 结构。
3. 事件由独立抽取器生成，保存参与者、对象、时间、立场、结果和最多三条事实作用。
4. 实体治理先做本体类型映射，再做同类型规范名/别名匹配、Embedding 候选和 LLM 裁决；歧义项隔离到 ReviewCase，不强制合并。
5. 事件参与者与语义实体共用 Entity ID；`EventEffect` 连接 Event 和 Assertion，并按有效时间更新 Assertion 生命周期。
6. JSON 保存可回滚快照，Neo4j 保存查询期协调图；写入前可用 SHACL 校验快照的部分结构。

### 3.2 查询阶段

1. Query Planner 生成实体、关系、时间、状态等共同提示。
2. vector、graph、event 三路并行召回；`ours_evolink` 当前默认三路都执行。
3. EvoLink 用实体、Assertion 和 Event 种子扩展协调图，产生补充关系/事件候选和可视化 Evidence Graph。
4. 各路分数不直接比较，而是按 `document_id` 做 RRF（`k=60`）；同一通路对同一文档只计一次，最终保留可追溯片段。

## 4. 当前指标情况

主实验是 MultiHop-RAG 固定子集：30 个问题、100 篇文档、443 个 Chunk。30 题都执行检索，但当前 scorer 只对其中 21 题计算 Gold Evidence 指标；另外 9 题是 `null_query`，不能把它们理解为系统无法回答。

| 方法 | Hits@10 | Evidence Recall@10 | Complete Recall@10 | MRR@10 | nDCG@10 | P95 延迟 |
|---|---:|---:|---:|---:|---:|---:|
| naive | 0.9524 | 0.6349 | 0.2857 | 0.7545 | 0.5612 | 8.33 s |
| hybrid | 1.0000 | 0.7302 | 0.4286 | 0.8147 | 0.6563 | 0.26 s |
| **ours_evolink** | **1.0000** | **0.8651** | **0.6190** | **0.8349** | **0.7280** | **17.81 s** |
| agentic_ours_evolink | 1.0000 | 0.8651 | 0.6190 | 0.7476 | 0.6870 | 26.32 s |
| ours_evoneed | 0.9048 | 0.7341 | 0.5238 | 0.7063 | 0.6185 | 24.05 s |

与 `hybrid` 相比，`ours_evolink` 的 Evidence Recall@10 提高 13.49 个百分点，Complete Recall@10 提高 19.05 个百分点，nDCG@10 提高 7.17 个百分点；代价是 P95 延迟高很多。通用 Agentic 版本没有增加证据覆盖，排序指标还下降；动态知识需求原型也没有超过固定三路。

同一数据与 scorer 下，外部适配结果为：HippoRAG 的 Evidence Recall@10 / Complete Recall@10 / nDCG@10 是 0.7540 / 0.5238 / 0.6469，E²RAG 是 0.6627 / 0.4286 / 0.4773，低预算 EventRAG 是 0.5635 / 0.2381 / 0.3282。由于切块、索引结构和适配条件不完全相同，只能作阶段性参考，不能作为严格同条件胜负结论。

协调图确实被执行：30 次查询累计产生 693 个实体种子、643 个 Assertion 种子、208 个 Event 种子，扩展出 854 个 Assertion、686 个 Event 和 213 条 EventEffect 关联。但“执行了扩展”不等于“每条扩展都正确或都有增益”。

实体治理的 20 篇 DWIE 小样本进一步显示：使用 Gold Mention 时，当前方法 Hard Entity F1 为 0.885，高于 Exact+Alias 的 0.724；但端到端 Mention Recall 只有 0.375，Hard Entity F1 只有 0.243，低于 LightRAG 的 0.566。说明治理本身有价值，当前抽取召回仍是明显短板。

### 指标结论边界

当前结果能支持“完整系统在这个小样本上提高了证据覆盖和完整率”。还不能支持以下结论：

- EvoLink 跨图连接单独造成了全部提升；
- EventEffect 链接、实体对齐和来源回链分别有多大贡献；
- 跨通路边本身是准确的；
- 结果在大样本、多随机种子、多领域和真实多模态输入上稳定成立；
- 当前延迟已达到生产可用水平。

最急需补的是同索引、同召回预算下的 `ours（关闭 link_evidence）` 对照，以及关闭 EventEffect、关闭实体治理、关闭来源回链的逐项消融。

## 5. 数据融合过程是否用到了本体

答案是：**用到了，而且与本体有实质关系；但关系只覆盖了融合链的一部分。**

当前已有静态本体 0.1.0：

- OWL 定义了 Entity、Assertion、Event、Mention、EventEffect 等核心类，以及科研技术领域的 Person、Organization、Model、Dataset、Device 等子类和部分关系。
- 实体类型 JSON 映射把抽取标签归一到允许类型；未知类型会进入歧义治理，实体自动合并原则上要求类型兼容。
- SHACL 在快照写入前检查部分必填字段、基数、状态和作用类型。
- 每个 Entity、Assertion 和治理决定记录 `ontology_version`；存量版本不一致时系统拒绝隐式升级。

所以，本体目前主要参与三件事：**统一类型语言、限制实体对齐、校验部分持久化结构。** EvoLink 的共享实体因此更稳定，跨路错连风险更低。

但融合并不完全由本体驱动：

- RRF、文档对齐、Mention 回链和查询期图扩展不依赖 OWL 推理。
- 关系谓词主要由代码中的关键词映射生成，未知词仍可变成开放谓词；OWL 中的关系集合没有成为真正的封闭约束。
- SHACL 转换时所有实体只写成通用 `tkg:Entity`，没有写入 `rt:Model` 等领域子类；Event、EventMention、事件参与边和很多时间/来源字段也没有完整进入校验图。
- Neo4j 保存的是属性图，当前查询没有消费 OWL/RDFS 推理结果。
- 还没有“有本体 vs 开放 Schema”的检索和融合质量消融。

因此准确说法是：**当前是静态本体约束下的部分本体化融合，尚未达到端到端 ontology-driven fusion。**

## 6. 要做到完整本体建模，还差什么

1. **建立单一 Schema 真源。** 类、关系、别名、抽取提示、代码映射和校验规则都从同一版本化本体生成，避免 TTL、JSON、YAML、Python 四处重复。
2. **实例真正落到本体 URI。** Entity 写入具体领域类，predicate 对应正式 ObjectProperty；Event、Mention、Effect、时间和来源关系完整 RDF 化，而不是只保存字符串标签。
3. **补齐语义约束。** 为关系增加 domain/range、逆关系、对称性、互斥类、必填字段、基数和时间一致性；SHACL 覆盖完整 TKG，而不是当前子集。
4. **让推理进入融合与检索。** 子类、等价类、同义关系、逆关系和约束结果应能影响实体合并、查询扩展、过滤和冲突判断，同时保留推理依据。
5. **补实例与本体质量评测。** 至少报告类型 F1、关系映射 F1、约束违反率、实体对齐 F1、EventEffect 链接准确率、来源回链准确率，以及本体开/关对检索指标的影响。
6. **提供正式迁移工具。** 现在只会拒绝版本不一致，还缺少从旧版本到新版本的实例映射、校验、回滚和重建程序。

做到这些后，才适合把系统称为“本体驱动的知识融合”，而不只是“带本体文件和类型约束”。

## 7. 要做到动态本体建模，需要什么

动态本体指 **Schema 自身受控演化**。公司更换 CEO、某关系被事件终止属于实例变化或 TKG 演化，不属于本体变化；新增 `AutonomousVehicle` 类型、拆分 `Device`、废弃一个关系才是本体演化。

推荐闭环如下：

1. **候选发现：** 从未映射类型/谓词、开放 Schema 抽取、频繁 ReviewCase、SHACL 失败和检索失败中收集新概念与新关系候选。
2. **证据聚合：** 为候选保存来源、出现频率、上下文、相邻概念、冲突情况和预期检索收益，过滤一次性噪声。
3. **变更判定：** 判断它是新增、重命名、合并、拆分、上下位调整、关系 domain/range 修改还是废弃。
4. **治理审批：** LLM 只能提议；规则检查和领域人员审批后才进入正式 Schema。候选、本体草案和发布版本必须隔离。
5. **版本发布：** 为每版保留稳定 URI、变更集、兼容映射、废弃标记和生效时间，支持旧查询映射到新版本。
6. **实例迁移：** 提供 dry-run、影响分析、批量迁移、重校验、重建索引、失败回滚和可重放日志。
7. **双版本查询：** 过渡期能够按本体版本读取旧实例，或把旧类/关系安全映射到新版，避免历史证据失联。
8. **回归评测：** 每次发布都比较覆盖率、未映射率、约束违反率、候选接受准确率、迁移完整率、旧查询兼容率、检索效果和延迟；无收益或破坏兼容时不发布。

最实际的实施顺序是：先补齐静态本体的单一真源与完整校验，再做“候选发现 + 人工审批 + 版本发布 + 迁移回滚”的半自动闭环，最后才考虑更自动的本体演化。让索引 LLM 直接修改生产 Schema 风险太高，不应作为第一版。

## 8. 下一步优先级

### P0：先把当前贡献证明清楚

- 补 `ours` 与 `ours_evolink` 的严格同条件对照。
- 做 EventEffect、实体治理、Mention 回链三个消融。
- 标注并评测跨通路边和 EventEffect 正确率。
- 报告索引成本、查询延迟和多随机种子方差。

### P1：完成真正的静态本体建模

- 统一 TTL、映射、Prompt 和代码枚举。
- 完整 RDF/SHACL 表达与验证 Entity—Assertion—Event—Mention—Effect。
- 让本体推理结果进入实体对齐和查询扩展。
- 做 ontology/open-schema 对照。

### P2：建立动态本体治理闭环

- 新术语候选池、变更分类与审批界面。
- 版本差异、兼容映射、实例迁移、回滚和重放。
- 每次 Schema 发布的约束、检索和历史兼容回归。

## 9. 最终判断

EvoLink 现在的强项不是“三路”这个数量，也不是用了 Neo4j 或本体文件，而是：**用共享身份把不同知识视图连起来，用 EventEffect 表达事件对 Assertion 生命周期的作用，并在查询时补回带来源的证据。** 当前小样本指标支持它对证据覆盖有价值，但机制归因、结构准确率、速度和规模化证据还不足。

本体已经参与实体类型、实体治理和结构校验，所以与数据融合有关；只是它还没有成为贯穿抽取、存储、推理、检索和版本迁移的统一语义底座。当前应称为“静态本体约束的部分本体化融合”。补齐正式 Schema 真源、完整实例映射、推理、质量评测和迁移工具后，才是完整本体建模；再加候选发现、审批、版本发布、兼容迁移、回滚和持续回归，才是动态本体建模。
